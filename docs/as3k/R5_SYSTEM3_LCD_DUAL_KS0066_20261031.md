## Existing implementation reused, not redesigned
- MC68EZ328 Port C data register PCDATA is at **0xFFFFF411**
  (0xFFFFF409 belongs to Port B, not Port C).
- PC0–3: LCD DB4–DB7; PC4: RW; PC5: RS;
  PC6: E1 / ks0066_0; PC7: E2 / ks0066_1.
- Existing driver lcd_port_c_commit implements atomic GPIO-to-KS0066
  transfers; existing screen_update combines both 2x40 controllers into
  a single 240x36-pixel 40x4 output (6x9 cells, 5x8 glyphs).
- No modifications to src/mame/skeleton/alphasma3k.cpp, core
  mc68328.cpp/h, LCD bridge, ROMs, CGROM or device configurations.

## Genuine firmware execution and graphics, independently on BOOT/WRITER
Using exact same debugger script and ROM settings in both tests:
- BOOT asma3ksb and WRITER asma3ksw both reached System 3 from
  real firmware initialization (R4 already proved CPU entry).
- Each executed **8,308 writes** to PCDATA 0xFFFFF411 by CPU;
  hardware control values yielded 1,492 E1 rising edges and
  1,270 E2 rising edges. Of those, 402 E1 and 370 E2
  rising edges had RS=1 (data rather than instruction).
- Probing with MAME program-space watchpoints avoids introducing any
  debug logic into the emulator source; scripts remain PRIVATE.
- Resulting debugger-generated snapshots under existing private path:
  r5_images/asma3ksb/0000.png and
  r5_images/asma3ksw/0000.png.
  Both PNG images are 240x36 RGB; ImageChops difference is empty
  (every pixel matches). Each shows 387 non-background pixels in
  row 1 and zero in rows 2,3,4 at the sampled moment.
- The readable original System3 message is
  "An unexpected data change occurred."
  The string exists literally in genuine
  OS3K_MIN_BOOT Flash offset 0x598D (one match; original System3
  OS3KROM source file offset 0x4198D); it is NOT generated by
  a synthetic MAME UI or emulator patch.
- At that point original System3 enters native key scanning at
  PC 0x004D0FD8, with key-list A4=0x0003FFBA and first
  two entries 0x0F/0x7F; the current idle-high Port D board model
  cannot deliver actual pressed keys. This is an input capability
  boundary, not an LCD rendering failure.
- The content of the displayed data-change warning is a real OS
  diagnostic; its deeper persistent-data reason is NOT established
  here. Do not infer from it that LCD hardware is faulty.
