## Actual manufacturer circuit and code, STATIC_FIRST
Original AlphaSmart 3000 PCB in alphasma3k.cpp identifies PDIUSBD11D.
Manufacturer development sources already mounted in Google Drive:
`ALPHASMART/Soruce code/Software/ModuleSources/UsbModule.c`,
`UsbAsmModule.s`, `UsbChip.c/.h`, `UsbIsr.c`, `UsbGet.h`,
`UsbToAS.c`, `UpdaterCommands.h`.
`UsbModule.c` selects EZ Port E GPIO for SCL PE2, SDA PE1, USB suspend
on a separate line; clears PEDATA bits and drives the two lines
**by toggling PEDIR** between output-low and input/released-high.
`UsbAsmModule.s` contains the original start/stop, byte-send,
byte-receive, acknowledgments and wait-for-clock routines.
Philips PDIUSBD11 product datasheet defines I²C command
7-bit address 0x1B (write byte 0x36), data 7-bit
address 0x1A (write 0x34, read 0x35). Command-read
byte 0x37 is invalid. Source:
https://www.fdi.ucm.es/profesor/mendias/DASii/docs/PDIUSBD11.pdf.
Original `UsbChip.c` sends commands D1 (address),
F3 (mode), F4 (interrupt read), and data in distinct
transactions, with repeated-start capability.

## Hardware change, same existing emulator
The MAME MC68EZ328 core previously notified board output
callbacks when **PEDATA** was written, but not on **PEDIR** or
**PESEL** changes. Its output readback also did not sample
an externally pulling-low device when configured for output-high.
This prevented the genuine bit-banged I²C sequence.

In `src/devices/machine/mc68328.cpp`:
- EZ Port E callback now receives effective open-drain level:
  actively output-low = 0; released/input = 1, including transitions
  produced by `PEDIR` and `PESEL`.
- EZ reading an output-high pin may observe an external device
  pulling that line low, as required for wired-AND SDA.
- Older non-EZ MC68328 behavior is retained.
- UART R10 bitstream callbacks remain independent and untouched.

In `src/mame/skeleton/alphasma3k.cpp`:
- The original EZ PE1/PE2 outputs/inputs connect directly to a
  board-level PDIUSBD11D I²C slave model in the EXISTING driver.
- Implemented start/stop, address matching (34/35/36),
  ACK/NACK, MSB-first byte receiving, SDA low drive for ACK,
  byte reads with master ACK/NACK, bus release, and repeated-start
  reset of transaction context.
- Implemented **limited** D11 command/data state for D1
  (USB address/enable), D8 (endpoint enable), F3 (mode/clock).
  F4 interrupt reads return 0000 when **no USB host or packet**
  has been connected; the emulator does not invent an endpoint
  packet or a false device enumeration.
- The I²C state and configuration bytes are reset and
  save-state registered.
- The model stays hardware-level and ROM-independent; no
  artificial text-output shortcut or direct USB file injection.

## Corrección de registros e índice RAM del D11 conforme a Philips (01/11/2026)

Esta es una corrección del MISMO trabajo R10, no otro
incremento ni una implementación de anfitrión USB.

Al confrontar el código `UsbChip.c/.h` del fabricante con
la hoja de datos Philips PDIUSBD11 (páginas impresas 3,
6, 8–10) se detectaron tres discrepancias en el hardware
antes emulado:
- Existen ocho endpoints USB funcionales, índices 2–9,
  con 8 bytes de datos cada uno; 0 y 1 no se consideran
  endpoints adicionales del AS3000. El arreglo interno de
  diez índices conserva el formato del hardware D11.
- `Read Endpoint Status 0x80+index` devuelve BUF_FULL
  en bit 5 (0x20), STALL en bit 3 (0x08). La lectura
  `Select Endpoint` sigue devolviendo únicamente FULL
  por bit 0 (0x01). Las marcas previas 0x01 para status
  y 0x80 para STALL **NO eran correctas** y quedaron
  expresamente reemplazadas.
- `Select Endpoint` (índices 0–9) inicializa el puntero
  a la SRAM de endpoint. `Read/Write Buffer F0` NO
  reinicia ese puntero: un buffer puede transferirse
  en varias transacciones I²C independientes.
- Se quitó la supuesta configuración de hub con `D0`
  del modelo: es un comando relacionado con PDIUSBH11,
  distinto del chip PDIUSBD11 propio del AS3000.
- `Read Last Transaction Status 0x40+index` se separa
  del estado del buffer y borra el bit de interrupción
  correspondiente, si se hubiera producido una transacción
  USB real. Sin un host, el valor real es 0.
  `Read Interrupt Register F4` entrega 2 bytes de
  estado, y limpia el indicador de bus reset al leerlo.

## Causas y correcciones demostradas

1. El núcleo EZ328 trataba GISR como un estado «en servicio» persistente.
   Al enmascarar una fuente retiraba la línea del CPU sin eliminar ese estado;
   al habilitarla de nuevo, el estado persistente impedía reactivar IRQ5 aunque
   siguiera pendiente. Se corrigió solamente la ruta MC68EZ328 para derivar
   ISR de IPR y las fuentes habilitadas y reevaluar las líneas de nivel.
   El comportamiento del MC68328 antiguo no se modificó.
   La ROM real instala System_HostInterruptHandler `004D0A26` y su vector
   de nivel 5 `004CD342`; `004D1648..004D1656` habilita IRQ5 antes de STOP.
   El STOP original está en `004D12BE`; el PC observable prefetched es
   `004D12C4`. No se escribe IMR, RAM ni ROM desde la aceptación USB.
   Esto explica por qué el forzado diagnóstico de IMR del handoff no bastaba:
   el estado GISR persistente seguía impidiendo reactivar la línea.
2. El puente esperaba SoftConnect en `04`, pero UsbChip.h/UsbMain.c y la
   ejecución original usan `10`: el firmware emite F3 `81` y luego `91`.
   Se corrigió la máscara y el reset del anfitrión en cada reconexión real.
3. Se respeta el byte `02` original de habilitación D8 para endpoints de datos.
   Los endpoints deshabilitados responden NAK; no se fabrican respuestas.
4. El adaptador USB/IP ahora separa el estado de cada URB, mantiene el orden
   de cada endpoint/dirección, serializa EP0 y permite OUT/EP0 mientras IN
   espera. Se verificaron respuestas simultáneas originales `01` y `58 02`.
   UNLINK elimina la solicitud pendiente sin RET_SUBMIT posterior:
   -104 para cancelación efectiva y 0 para cancelación tardía.
   Se corrigieron longitudes OUT, campos reservados de RET_SUBMIT, timeout
   durante espera de conexión, OUT de longitud cero y errores/desconexión TCP.
   Límites implementados: 64 URB pendientes, 1 MiB por transferencia,
   2 MiB de entrada aún no analizada. El socket es opt-in y loopback.

La reproducción inicial del binario recibido volvió a producir EOF 0/48 en
GET_DESCRIPTOR. Con el estado persistente acreditado, IMR superior era `00EF`
por acción de la ROM, ICR leído como palabra era `0080`, IPR/ISR superior
`0010`, y el CPU se quedaba en STOP. El handoff con arranque distinto mostraba
`00FF`: no se presenta ese valor histórico como una nueva observación idéntica.
Tras las correcciones se observan F3, reset de bus, ejecución USB y los datos
firmware auténticos. Al estar IRQ5 enmascarada por la ROM, ISR superior vuelve
correctamente a `0000` incluso si IPR conserva `0010`.

SET_CONFIGURATION: `00 09 01 00 00 00 00 00`, estado IN ZLP, status 0.
GET_CONFIGURATION: `80 08 00 00 00 00 01 00`, respuesta `01`.

Datos enviados y recibidos, 47 bytes idénticos en ambos sentidos:
`52313020555342206f726967696e616c3a20323032362d31312d3035202f20416c706861536d61727420333030300d`.
Texto: `R10 USB original: 2026-11-05 / AlphaSmart 3000` seguido de CR (`0D`).
CLEAR_FILE `04` -> `44`; SEND_FILE_TO_AS `06 00 00 00 2F` -> `46`;
FILE_BUFFER `08` + segmentos de hasta siete bytes de texto;
GET_FILE_SIZE `01` -> `41 00 00 00 2F`; GET_FILE_FROM_AS `07` -> seis paquetes
IN: 8+8+8+8+8+7 bytes. Todos los bytes y respuestas constan en transactions.json.
Una prueba diagnóstica CRLF anterior devolvió CR sin LF por comportamiento de
la ROM; se conserva como observación. La aceptación final usa CR nativo y
comprueba igualdad byte a byte, sin normalizar los datos recibidos.

## Límites de lo acreditado

La aceptación usa un anfitrión independiente real mediante USB/IP loopback y el
protocolo AlphaSmart/Get original ejecutado por la ROM. El puente abstrae el
controlador anfitrión a nivel de paquetes USB. No se acreditan PHY NRZI/CRC bit
a bit, attach kernel VHCI, la aplicación gráfica Windows/Mac del fabricante,
impresoras, updater ni transferencias ISO. No se hicieron esas pruebas.
Los avisos anteriores KS0066 F05 NEEDS REDUMP y accesos FFFFFD0C/0E permanecen.
No impiden los cuatro criterios reproducidos; no se presentan como corregidos.
DEVLIST/IMPORT se mantienen como metadatos del transporte, sin contar como
respuesta de firmware. Ningún descriptor ni eco de archivo se genera en C++.
